# 从简短需求到条件明确的交付方案

本页是本工具包的工程归纳，不是 PDF 提供的标准架构。技术分类用于选择，不要求每个项目使用全部组件。

## 1. 先找到值得验证的问题

把“想要AI”转成：谁在什么流程中受阻、造成什么损失、当前如何处理、什么结果值得投资。
沿着“表面抱怨 → 工作步骤 → 数据/规则/协作原因 → 可测业务影响”找根因。DW-08展示了物料搜索到采购浪费的链路。

记录业务Owner、数据Owner、实际使用者与最终决策者；谁获益、谁增加负担、谁会抵触。需要多个部门配合时，先确认能推动协作的人。
没有基线时，先定义采样而非编造ROI。客户价值和交付方工时、维护及定制成本分别估计。

## 2. 技术选择顺序

| 可观察条件 | 首先试验 | 参考案例 |
|---|---|---|
| 流程仍纸质、字段与口径不一致 | 表单、数据标准化、数据库/BI | DW-13、18、20、24 |
| 输入输出明确、规则稳定 | 公式、SQL、脚本或固定工作流 | DW-22 |
| 多格式文本/图片需结构化 | OCR/VLM抽取＋格式校验＋人工异常队列 | DW-02、09、10、19 |
| 需要找企业已有知识 | 权限过滤、检索、来源引用、知识更新 | DW-01、03、08、11 |
| 需要精确空间、数值或专业计算 | 专业算法、规则引擎、GIS/CAD工具 | DW-04、06、21 |
| 多步骤可预先确定 | 有状态的固定流程与重试/幂等设计 | DW-05、12、15、17、23 |
| 下一步确实依赖语义判断、路径不能预定 | 有边界的工具调用Agent | DW-04、16 |
| 技术已可用但组织不使用 | 知识萃取、培训、激励及责任调整 | DW-07、14 |

先选择一个主模式，只有真实依赖需要时再组合。表格不是排他分类；有知识库不意味着一定要向量库，有复杂流程不意味着多Agent。
金额、几何、规则边界以确定性工具与专业审核为准；LLM用于抽取、理解、解释或有边界的调度。
知识萃取先于RAG；实际任务结果必须返回用户的既有工作入口。

## 3. 三条路径必须有不同的依赖条件

- **A 主方案**：在已确认的数据、接口、预算和权限下，最接近业务目标的最小方案。
- **B 备用方案**：接口、实时性或模型质量不达标时，采用较低依赖的CSV批处理、规则或人工复核路径。写清损失的能力和切换条件。
- **C 人工兜底**：数据缺失、无权处理、风险不可接受或两方案均失败时，保持原业务、暂停自动动作并交给指定负责人。

切换模型/云厂商、API转浏览器操作、扩大数据上传均可能改变权限和数据目的地，备用方案不自动继承授权。
可降低时效/覆盖度，不能悄悄降低安全与专业责任要求。

## 4. 逐项过关，而非一个总分掩盖硬阻塞

1. **价值**：业务影响和机会成本可解释；验证预算有上限。
2. **数据与知识**：有合法来源、样本、口径、质量和更新责任。
3. **集成**：在实际环境只读验证访问；接口与输出格式可用。
4. **安全与责任**：权限边界、人工审批、退出与失败处理明确。
5. **经济性**：客户收益与交付维护成本分别核算；未知项列假设。
6. **采用**：使用入口、培训、利益变化和反馈渠道明确。
7. **验收**：基线、样本、失败样本、测量方法和签收人事先约定。

缺失项只阻止依赖它的结论/动作。接口未知仍可做脱敏样本验证；无生产写入权则止于建议/草稿，不阻止只读诊断。

## 5. 先验证，再投入

最小样本验证 → 只读/影子运行 → 人工确认试点 → 受控扩大 → 回访。
每一阶段写输入、预期、异常、责任人与停止条件。回访时间由业务周期确定，不能把固定30/60/90天当普适规则。
交付不仅是结果正确：还包括谁使用、在哪个系统、什么格式、可否编辑、如何追溯和恢复。DW-06的截面图和DW-21的CAD初稿体现此边界。
