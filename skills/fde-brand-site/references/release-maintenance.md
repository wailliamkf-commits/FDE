# 实施、发布与持续优化

## 1. 接管与最小实现

核对正式域名、商店/项目ID、当前线上主题、预览主题、读写账号、可用工具与发布权限。插件与浏览器可能连到不同商店；身份不一致就停止该写入通道，保留其他独立工作。已有代码/用户修改先读diff；主题保留平台设置，不全量覆盖商店配置。

建立依赖顺序：事实/翻译→素材上传完成→模板/模块→样式与脚本→路由/链接→预览→发布→公开回读。长文本输入需验证完整性；保存后重开，字符数只是辅助，关键内容与公开渲染另验。超时先检查是否已写入；异常未保存缓冲区先恢复，不重复叠加输入。

优先目的明确的模块和局部命名空间；重复网格类名可能互相覆盖，模板逻辑应可读可测。保持原生表单/政策/翻译约定；无库存时采用诚实咨询，不用伪商品补页面。新服务、数据库、后台常驻进程只在有实际需求和授权时引入。

## 2. 发布Gate（分别记状态）

| 层级 | 证据 | 不能推导 |
|---|---|---|
| LOCAL | 检查器、单测、构建/语法、数据契约 | 线上已保存或视觉正确 |
| SAVED | 精确对象、文件重开/回读、版本 | 正式主题正在使用它 |
| PREVIEW | 正确预览ID的浏览器实测 | 公开域名已改变 |
| PUBLISHED | 当前发布角色/ID、正式URL载荷/素材 | 真实付款、送达、顾客采用 |
| VERIFIED | 冻结范围的实屏、实际操作、异常/回归 | 全设备、法律合规或商业结果 |

BLOCKER必须修复；SHOULD_FIX在本轮低风险内修；OPTIONAL排队。权利/库存/税运/支付/客户信息不完整时可以只放行真实内容与询盘页面，但不能放行伪交易或隐瞒强制披露。规则变更需理由和重测，不能删失败断言凑PASS。

## 3. 测试矩阵

内容：标题/主张/日期/价格范围/交期起点/政策摘要一致；没有假证据。路由：状态码、canonical、内链、地图、404/空状态。代码：相邻模板、翻译缺项、无效参数、数据兼容、XSS/隐私边界。视觉：桌面/手机、图像构图、字体、对比、200%放大等适用项目。交互：键盘、返回、菜单、tabs、表单错误、加载/失败、减少动态、无JS核心内容。真实提交/收款等有副作用的测试另取对应授权。

性能：固定设备/网络/缓存条件，记录多次冷启动及分布，而不是一次高分。核心Web指标LCP/INP/CLS用真实用户75分位标准评估；实验室LCP/TBT和浏览器交互观察不可冒充真实用户INP。没有CrUX/RUM数据就明说。检查LCP资源、尺寸/DPR、传输字节、图片解码、字体和布局抖动；用同环境前后对比，不把运营商CDN波动当作代码收益。

## 4. 优先级与实验闭环

从证据写问题→影响用户任务→可能原因→最小改动→风险→指标/回滚。先可用性/事实错误，再加载/选择成本，再可读性/发现，再视觉可选项。可用影响×覆盖×信心÷成本排序，但评分是决策辅助，不是事实。

每版只处理有限关联问题；例：响应式图片体积→合理srcset与格式→保留原图身份与alt→请求字节/构图对比；不是同时改首页文案、价格和结账后无法归因。上线后立即回归，之后按真实流量/报错/反馈更新。重复低价值模块可删减，新增图应说明它替代了哪个信息缺口。

## 5. 长期维护与存储

默认计划节奏（不是自动任务已创建）：发布后关键路线检查；有运营能力时按风险定期检查链接/表单/性能；按月复盘内容与漏斗；供应商、政策、平台变更触发即时审核。指定负责人、响应方式与暂停/回滚条件。用户要实际监控才配置平台调度，不能靠本地Chrome永远开启。

主题源代码和通用方法可以在私仓版本管理；秘密不进Git，客户/证书/订单资料独立权限存储。Shopify承载商店、云对象存储/CDN承载媒体；GitHub私仓不使公开部署的网站自动私密，也不替代交易数据库或服务器。

单一有效源码、一个约定回退、最终素材、必要原始证据、最小状态/测试报告。临时文件放专用路径，清理先确认引用/任务状态/保留期/所有者，先预览再按用户授权移入可恢复废纸篓；不要删除仍被线上主题引用的素材。原始证据和订单合规留存不按缓存规则删除。备份应验证可恢复，不能只检查文件存在。
